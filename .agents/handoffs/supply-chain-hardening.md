Three of the four remaining stack-hardening items in the improvement program.
Coverage thresholds are not here; see below.

## Behavior changed

None in the product. What changes is what a future `npm install` and a future
workflow run are allowed to resolve to.

## GitHub Actions are pinned to commits

Every `uses:` ran on a movable tag — `actions/checkout@v4`,
`actions/setup-node@v4`, `actions/checkout@v6`, `gitleaks/gitleaks-action@v3`.
A tag is a pointer that the action's owner can move, and whatever it resolves to
runs inside our workflow with our permissions and our secrets. The third-party
one, `gitleaks-action`, carries the most of that risk.

All eight references now name a commit, with the release in a comment so the pin
stays reviewable:

| Action | Release | Commit |
| --- | --- | --- |
| `actions/checkout` | v4.4.0 | `11d5960a326750d5838078e36cf38b85af677262` |
| `actions/checkout` | v6.1.0 | `d23441a48e516b6c34aea4fa41551a30e30af803` |
| `actions/setup-node` | v4.4.0 | `49933ea5288caeca8642d1e84afbd3f7d6820020` |
| `gitleaks/gitleaks-action` | v3.0.0 | `e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e` |

Each moving tag pointed at exactly that commit when it was resolved, so nothing
changes about what CI runs today.

`ci.yml` uses checkout v4 and `secret-scan.yml` uses v6. That inconsistency is
left alone deliberately: pinning is not the same change as a major upgrade, and
mixing the two would hide one inside the other. It is worth a follow-up.

## Dependencies that reach something are pinned exactly

Nine direct production dependencies moved from a caret range to an exact
version. They were chosen by what they can reach, not by popularity: they hold a
credential, speak to something outside the process, or parse bytes a person did
not write.

`@supabase/ssr` and `@supabase/supabase-js` (sessions and all data access),
`groq-sdk` and `resend` (outbound, credential-holding), `archiver`, `yauzl`,
`csv-parse` (an imported vault, a pasted CSV), `react-markdown` and `remark-gfm`
(Markdown from somewhere else, rendered into the DOM). `next` and `zod` were
already exact.

Every one resolved to its range's floor already, so **nothing installed
changed**: the lockfile diff is nine declared ranges and zero `version`,
`resolved` or `integrity` lines. 857 locked packages before and after.

`npm ci` was already deterministic because of the lockfile. What the pin
prevents is a future `npm install` or an unattended bump quietly resolving code
nobody has looked at into exactly those paths.

Five TipTap packages and `@types/archiver` are still ranges, on purpose: TipTap
is five packages that must move together, and a types package does not ship.

## A release dependency inventory

`docs/engineering/dependency-inventory.md`, generated by
`npm run inventory:dependencies`, read from the lockfile and nothing else.

Reading from the lockfile rather than `node_modules` is the design decision
worth knowing about. Roughly a third of the production closure — 45 of 412 — is
platform-optional, so any field read from the installed tree would differ
between a macOS laptop and Linux CI, and a drift check over it would fail for
the wrong reason. Licences are the obvious missing column and the reason to
revisit this with a real SBOM tool rather than to read them from whatever
happens to be installed here.

28 direct production dependencies, 22 exact. 412 in the closure. One registry.

## Four guards, each demonstrated by breaking it

`web/tests/unit/supply-chain.test.ts` runs in the ordinary unit suite and shares
its inventory builder with the generator, so the file and its check cannot be
built from different logic. Each was verified by violating it:

- an action back on `@v4` → fails, naming the file and the reference;
- a pinned commit with its release comment removed → fails;
- `@supabase/ssr` back on `^0.12.3` → fails, naming the package;
- a hand-edited inventory → fails.

## A correction to eight earlier handoffs

Every handoff in this stack recorded `npm ci` as installing **770 packages**.
The real figure is **768**, measured on this branch and again on
`codex/operation-contract-manifest`, which has an identical lockfile — nothing
after `238eace` touches it, so 768 held for all of them. Four of the eight are
mine and I carried the number from the program's stated baseline instead of
reading my own output. All eight are corrected.

The earlier figure may be what a different npm reported; the point is that the
number is now one I measured rather than one I repeated.

## Risks and follow-up

- **Coverage thresholds are not done.** They are the fourth stack item and the
  only one that is a judgement rather than a mechanism: a number picked without
  agreeing which paths are critical becomes something people optimise around.
  The Operation execution path, the undo path, and the import parsers are my
  candidates, and that list wants agreement before a threshold is set.
- Pinning trades a silent upgrade for a visible one. These eleven packages will
  now need deliberate bumps, and a security release will not arrive on its own.
  That is the intent, but it is only safe if something watches for advisories —
  `npm audit --audit-level=high` runs in CI, which covers known ones.
- The inventory carries no licences, as above.
- The checkout v4/v6 split is unresolved.
