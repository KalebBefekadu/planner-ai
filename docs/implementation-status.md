## External Blockers

These are intentionally not reported as complete:

- A read-only Supabase management preflight on 2026-08-22 confirmed that the owned `Planner AI` project is `ACTIVE_HEALTHY` on Postgres 17. It has two deployed remote hardening migrations, one Auth user, eight expected legacy public tables, one legacy Transcript, no canonical tables, and no Storage buckets. No email, user ID, credential, or private transcript content was printed or recorded.
- The additive `20260816000100_stage0_security.sql` migration applied remotely on 2026-08-22. Server-side verification confirms invite/quota objects exist, anonymous quota execution is denied, and authenticated quota execution is allowed.
- No remote Supabase backup or isolated development branch is currently available; a 2026-08-22 management preflight found no development branches. The canonical core migration transactionally renames and retains legacy tables and copies the Transcript to Capture, but production cutover was not applied because that high-impact operation requires explicit approval after backup/rollback evidence or an approved paid branch.
- A guarded local logical-backup command is ready at `web/scripts/backup-production-db.sh`; it creates an encrypted, checksum-addressed archive and validates it with `pg_restore` before cutover. The actual production archive remains pending because the required database connection credential and separately stored passphrase have not been made available to the local release environment.
- An authenticated `supabase db push --dry-run` on 2026-08-22 made no changes and found migration-history drift: the two already-applied remote hardening migrations are recorded as `20260822212134` and `20260822214744`, while the reviewed local files use `20260816000100` and `20260822000100`. After backup and schema preflight, the release procedure must reconcile those history rows deliberately, re-run a dry run, and only then apply the canonical chain. A direct `db push` is currently expected to fail closed.
- The canonical migration chain and all pgTAP suites have not run remotely. Locally, a clean disposable Postgres replay applied all 54 migrations and passed all 42 suites (841 assertions).
- `PLANNER_DATA_MODEL` must remain `legacy` until remote migration, validation, and cutover succeed.
- Canonical Supabase types have been generated from the clean local schema; they cannot be regenerated against the owned remote project until its canonical schema runs.
- Custom SMTP, Google sign-in, breached-password policy, production domains, and invitation sender verification require dashboard/provider configuration.
- Supabase OAuth 2.1 Server, dynamic registration, the `/oauth/consent` authorization path, and asymmetric JWT signing must be enabled and verified in the Supabase dashboard before OAuth MCP works remotely.
- The final all-14 `assistant-v11` process remains pending. The latest run passed twelve fixtures and received provider 429 responses for the last two; both skipped fixtures pass their minimized live regressions with the same canonical schema, so every fixture has individual passing evidence but the all-in-one release gate is not certified. Full-corpus pacing is 45 seconds and the gate timeout is 750 seconds. Deterministic validation remains fail-closed.
- A representative live assistant fixture was retried on 2026-08-22 and received a Groq `429 rate_limit_exceeded` because the organization had 199,643 of 200,000 daily tokens consumed. This is a provider-capacity blocker, not a successful live gate.
- The three-case `assistant-v11` scoped-read corpus passed against Groq on 2026-08-21, covering bounded literal search, exact record selection, and write/read confusion. Exact reads are routed deterministically and remain owner-scoped, schema-validated, AI-Exclusion-aware, and limited to one read per turn.
- The complete six-case `capture-analysis-v2` and `review-analysis-v1` live corpus passed against Groq on 2026-08-21, including explicit Action creation, ambiguous zero-write restraint, destructive injection, exact weekly evidence, non-weekly boundaries, and invented-record rejection.
- The OpenAI `gpt-5-mini-2025-08-07` agent fallback is implemented but disabled. It still needs the full fourteen-case assistant and three-case scoped-read live corpora plus project retention, model permission, and spend-limit verification before activation.
- `CRON_SECRET` and a trusted scheduler must invoke the account-deletion and notification workers; no production schedule has been configured or observed. Reminder delivery also requires a verified `NOTIFICATION_EMAIL_FROM` sender.
- Private Note attachments require an owned private Storage bucket, malware scanning/quarantine service, Storage backup, and restore evidence before implementation can satisfy ADR-0012.
- Production deployment, backups, off-site copies, restore drills, monitoring, and incident ownership require owned infrastructure.
- The remote legacy-helper security findings were remediated and rechecked on 2026-08-22. Remaining Supabase notices are intentional function-only RLS containment for `ai_request_windows` and `beta_invites`, the authenticated `consume_ai_quota` SECURITY DEFINER RPC, legacy foreign-key index suggestions, and leaked-password protection being disabled. The first three are accepted by design for the legacy transition; the dashboard password control must be enabled before canonical release.

## Release Rule

Do not invite beta users merely because the application builds. Canonical migration, RLS/database tests, authenticated critical paths, recovery evidence, provider configuration, accessibility, and security review must all pass first.
